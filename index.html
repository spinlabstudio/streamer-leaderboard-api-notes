Designing a streamer leaderboard API for an online casino

Streamers and their communities like a race: whoever wagers most with the streamer's code this month wins a share of a prize pool. The leaderboard shows on stream as an overlay and on the streamer's own site, which means it is read by thousands of people at once and attacked by anyone who wants the prize. This is how I would shape the API. The endpoint names are an example design, not any vendor's actual interface.

1. Model the race, not just the ranking

A leaderboard belongs to a campaign: a streamer or affiliate code, a time window, a scoring rule and a prize table. Make the campaign a first-class object and the leaderboard a view of it.

GET /v1/campaigns/{campaign_id}
{
  "campaign_id": "nov-race-01",
  "code": "STREAMERX",
  "starts_at": "2026-11-01T00:00:00Z",
  "ends_at":   "2026-12-01T00:00:00Z",
  "metric": "wagered",            // or "net_wagered", "points"
  "currency": "EUR",
  "prizes": [{"rank": 1, "amount": "500.00"}, {"rank": 2, "amount": "250.00"}],
  "status": "live"                // scheduled | live | settling | final
}

2. The leaderboard endpoint

GET /v1/campaigns/{campaign_id}/leaderboard?limit=20
{
  "as_of": "2026-11-05T09:15:00Z",
  "entries": [
    {"rank": 1, "player": "ma***88", "score": "18240.50"},
    {"rank": 2, "player": "jo***k",  "score": "17110.00"}
  ],
  "next_update_in_seconds": 60
}
  • Mask player names server-side. Never send a full username or player ID to a public overlay, and let players opt out of appearing at all.
  • Send scores as decimal strings so JavaScript overlays don't render 17110.000000002.
  • Return as_of so the overlay can show "updated 1 min ago" and nobody argues about a stale screenshot.

3. Scoring rules that survive abuse

Raw wagered amount is the easiest metric and the easiest to game. A player can wager €10,000 on a 99% RTP game or on both sides of a roulette bet at almost no cost. Defences that work:

  • Weight by game type: count slots at 100% and low-edge table games at a fraction, the same way bonus wagering contributions work.
  • Exclude hedged and very low-risk bets, e.g. covering most roulette numbers, or sports bets below a minimum odds threshold.
  • Exclude bonus-funded stakes or count them separately.
  • Cap per-bet contribution so one huge spin can't decide the race.
  • Freeze at ends_at, then settle: switch status to settling, run fraud and duplicate-account checks, and only then publish final. Prizes are paid on the final list.

4. Built for overlay traffic

An overlay polling every 5 seconds from 3,000 viewers is 600 requests per second for one streamer. Never compute the ranking per request.
  • Recompute rankings on a schedule (every 30–60 s) or on a stream of bet events into a sorted set, and serve a cached snapshot.
  • Set Cache-Control: public, max-age=30 and put the endpoint behind a CDN. The data is public by design.
  • Offer a server-sent events or WebSocket feed for overlays that want live updates, publishing only when the top N changes.
  • Rate-limit per API key and issue keys per streamer, so a leaked key can be rotated without breaking everyone.

5. Endpoints for the streamer's own tools

GET /v1/campaigns?code=STREAMERX&status=live,final   // history for their website
GET /v1/campaigns/{id}/me                           // authenticated player: own rank and gap to next
POST /v1/webhooks                                   // notify on rank change in top 3, on final

The /me endpoint is the feature players love: "you are 14th, €320 behind 13th". Keep it authenticated and never expose other players' exact data through it.

6. Compliance notes

Wagering races encourage more play by design, so check whether your licence allows them in each market, and how. Exclude self-excluded players, players on a time-out and anyone under safer-gambling review automatically, and show the full terms (scoring rule, exclusions, prize table) on a public page linked from the overlay.
